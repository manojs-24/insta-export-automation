## Commands

Use `uv run` (it manages `.venv`; no manual activation). Python >= 3.14.

```
uv run pytest                          # all tests (~20s; launches real Chrome headless)
uv run pytest -m "not browser"         # fast tests only, no Chrome
uv run pytest tests/test_browser.py::test_profile_persists_across_sessions   # single test
$env:WA_TEST_HEADED="1"; uv run pytest # watch Chrome during browser tests (PowerShell)

uv run web-automation --keep-open      # headed smoke test (or start.bat)
uv run web-automation --inspect --keep-open --url https://www.instagram.com/   # save accessibility snapshots to logs/inspect/ for selector discovery
uv run web-automation --config configs/instagram_export.json [--validate-only]   # run / just validate a JSON automation (exit 2 = a step failed, exit 3 = a guard stopped the run on purpose, e.g. an export is already pending; nothing submitted)
uv add <pkg>                           # then regenerate requirements.txt:
uv export --format requirements-txt --no-hashes --no-emit-project -o requirements.txt
```

`requirements.txt` is a snapshot of `uv.lock`; `uv.lock` is authoritative. No linter is configured.

## Architecture

Package `src/web_automation/` (the build backend is pinned with `module-name = "web_automation"` in `pyproject.toml`, which differs from the project name `web-automation-engine`).

- `browser/manager.py`: `BrowserManager` owns the Playwright driver and one Chrome **persistent context** (`launch_persistent_context` with `channel="chrome"`, i.e. the installed Google Chrome, never bundled Chromium). Use it as a context manager so Chrome always closes; `start()`/`stop()` are idempotent. Launch failures (including a profile locked by another Chrome) become `BrowserLaunchError`.
- `browser/session.py`: `BrowserConfig` (frozen dataclass; defaults are headed + `chrome` channel per the README) and `BrowserSession` (context + primary page).
- `settings.py`: `Settings.load()` reads `WA_*` env vars / `.env` (see `.env.example`); real env vars override `.env`. `main.py` CLI flags override Settings for one run. `.env` may optionally hold `WA_IG_USERNAME`/`WA_IG_PASSWORD` (never the OTP); they are hidden from `repr` and must never be logged.
- Logging: `utils/logger.configure_logging()` only adds a console handler; there is NO log file and no `WA_LOG_DIR`. The permanent log is the `wa_logs` table (filled by `db/history.RunRecorder`). `logs/inspect/` still holds `--inspect` snapshots.
- `utils/`: `exceptions.py` (all errors derive from `WebAutomationError`) and `logger.py` (loggers under the `web_automation.*` namespace).

- `actions/`: each action is an `Action` subclass with a `name`, added to the registry by `@register_action` (`base.py`); `actions/__init__.py` imports every module so they self-register. Adding an action = new class + decorator. `locators.py` turns a JSON selector spec (role/label/placeholder/text/css/xpath) into a Playwright locator and `find()` waits for visibility; ambiguous or missing elements raise, never fall back to another element. `fill` can read its value from an env var (`value_env`) so secrets stay out of steps.
- `engine/`: `Executor.run(steps)` validates ALL steps (known action, unique ids) before running any, then executes sequentially. Any step may carry a `when` condition (`{"variable", "equals"|"not_equals"}`) on a variable set by an EARLIER step's `save_as` (checked at config load and again before running); an unmet condition gives status `skipped` and the run continues. `ensure_login` has `save_as` -> `logged_in`/`already_authenticated`, and the post-login popup steps in `configs/instagram_export.json` run only on `logged_in`. A failed step logs its message and a query-stripped URL (the project takes and stores NO screenshots), and (`on_failure="stop"`) skips the rest; a declined `confirm` always stops. Non-engine exceptions (real bugs) propagate. `ExecutionContext` carries the page, timeouts and injectable `notify`/`wait_for_user`/`confirm_with_user` callbacks (tests replace the console prompts). Results never include extracted values.
- `browser/instagram_login.py` is interim M1 code (auto-login from `WA_IG_*`; when Instagram asks for a verification code it prompts in the terminal via `ctx.ask_secret`/getpass (hidden, never logged, max 2 submissions) and types it into Chrome, falling back to waiting for manual entry); M4 should replace it with config-driven steps.

- `actions/downloads.py`: `download_latest_export` picks the finished export row (has a Download control, text matches `row_contains`) with the latest "Expires on" date and saves it under `ctx.export_dir` (with `delete_old`, only after the new file is verified, every other top-level file of that extension in `save_dir` is deleted so just the latest download remains); `extract_from_zip` copies one member out atomically (size-capped, optional JSON validation, old file kept on failure). All paths are resolved inside `ctx.export_dir` (`WA_EXPORT_DIR`, default `exports/`); `..`, absolute paths and drive letters are rejected both by the schema and at run time. A request just raised is still "Requested", so the download normally takes an earlier finished export; none ready => status "stopped".
- `config/`: `schema.py` is the Pydantic model of the JSON file: a discriminated union with one model per action (closed set; `extra="forbid"` so typos fail; `http(s)` URLs only; `fill` with a password-like selector must use `value_env`). `loader.py` reads/validates and formats errors WITHOUT echoing input values. `AutomationConfig.to_steps()` converts to engine `Step`s and `engine/runner.py:run_config` applies `execution.timeout`/`on_failure`. **Adding an action needs both an `Action` class and a schema model**: `test_every_registered_action_has_a_schema_and_vice_versa` enforces this.

- `db/` (Milestone 5; hosted Postgres via `WA_DATABASE_URL`, driver psycopg 3): `schema.sql` is applied idempotently (`wa_` tables: runs, run_steps, logs, followers, follower_events). `history.RunRecorder` records a run and buffers log lines, and NEVER lets a database problem stop an export (after the first failure it stops recording and the run continues; console and `logs/` still have everything). `followers.sync_followers` keeps `wa_followers` equal to the latest list in one transaction: new followers are inserted with `added_at=now()`, followers missing from the list are deleted (audit rows go to `wa_follower_events`), existing rows are untouched; an empty list, or one that would delete >50% of 20+ stored followers, is refused. The `sync_followers` action reads `followers_1.json` straight from the zip, so nothing is written to disk and usernames are never logged. `engine/report.py` derives submitted / acknowledged / downloaded / completed as separate facts from step results (clicking the button alone is not success). The DB URL contains a password: `connection.connect` re-raises driver errors as `DatabaseError` with only the error class + SQLSTATE; never log or print the URL (use `describe`).
- The user confirmed against their hosted Postgres that the connection works and rows are being written. `tests/test_db_integration.py` has not necessarily been run by them.
- `uv run web-automation --db-check` connects, creates missing tables and prints row counts. `tests/test_db_integration.py` runs against a real Postgres only when `WA_TEST_DATABASE_URL` is set, inside a throwaway schema it drops afterwards.

`exporters/` from the README layout is superseded by `db/`.
- `web/` (local UI, `uv run web-automation --ui` or `start_ui.bat`): `app.py` is a FastAPI app serving one static page (`static/index.html|app.js|style.css`, plain HTML, no framework, everything inserted as text, strict CSP so no inline script) plus a JSON API. Security model: listens only on 127.0.0.1 (`serve` refuses anything else). Two ways in, chosen by `.env`: LOGIN mode when BOTH `WA_UI_USERNAME` and `WA_UI_PASSWORD` are set (password >= 8 chars; `web/auth.py`): the page shows a sign-in form, a correct login sets an HttpOnly + SameSite=Strict `wa_session` cookie (random, only its hash is kept in memory, 12 h, max 20 sessions, lost on restart), 5 wrong attempts in 5 min lock ALL logins out for 5 min (429 + Retry-After), the link token is ignored in this mode, and a half-set pair is refused at start-up. TOKEN mode when neither is set: every `/api` call needs the random per-start access token (header `X-Access-Token`, constant-time compare via `tokens_equal`; printed as a link whose `#token=` fragment the page moves to sessionStorage). cross-site `Origin` and non-loopback `Host` values are refused (CSRF / DNS rebinding), no OpenAPI docs. `runner.WebRunner` runs ONE workflow at a time on a background thread; questions a run asks (OTP via `ctx.ask_secret`, "press Enter", yes/no) become a `question` in `/api/run` that the page answers via `/api/run/answer`; the OTP lives only in memory, is never echoed, logged, stored or returned by any endpoint, and unanswered questions time out (10 min) or are cancelled. `engine/service.py:execute_on_page` is the shared "run a config and record it" path used by both the CLI and the UI. `db/queries.py` holds the read-only SQL (all values are parameters; LIKE wildcards are escaped). Scheduling (`web/scheduler.py`, APScheduler `BackgroundScheduler` inside the UI process, so automatic runs happen ONLY while `--ui` is open): `WA_SCHEDULE_MINUTES` (0 = off, 5-10080; below 5 is rejected so a typo cannot flood Instagram), `WA_SCHEDULE_CONFIG` (bare *.json name in configs/), `WA_ANSWER_WAIT_MINUTES` (1-240, how long ANY run waits for the OTP/answer; an explicit `WebRunner(wait_timeout_s=...)` overrides it, used by tests). The first automatic run is one full interval after start-up. `RunScheduler.tick()` never starts a second run (skips with a warning if busy). Every run stores `trigger` = `manual` (button/CLI) or `scheduled` in `wa_runs.trigger`, shown in the Runs tab ("Started by"), the dashboard's last run and the run details; the HTTP API always uses `manual` (a forged `trigger` field is ignored). Loading states in `static/app.js`: a top progress bar (`#loadbar`, counted per outstanding request) plus a spinner row per table; background polling passes `{quiet: true}` so it never flashes the bar; each section tags its requests so a slow older response cannot overwrite a newer one. `tests/test_web_loading.py` checks this in headless Chrome against a deliberately slow fake database. NOTE: the CSP forbids `unsafe-eval`, so tests must not use `page.wait_for_function` with a string expression; poll with Python instead.
- **Retries:** a step may carry `"retry": {"max_attempts": 2-5, "delay_ms": optional}`. Each action declares a `retry_policy`: `RETRY_NEVER` (default for any new action; submit-like or side-effecting actions: `enter_password`, `ensure_login`, downloads, `sync_followers`, `confirm`, ...), `RETRY_PRE_ACTION` (`click`/`fill`/`select`: only retried when `ElementNotFoundError`, i.e. nothing was clicked or typed yet) or `RETRY_ANY` (read-only/idempotent: `navigate`, `wait`, `verify`, ...). Setting `retry` on a NEVER action is rejected both by the schema and by the executor before anything runs. A guard stop, a declined confirm, bad parameters and unexpected bugs are never retried. `StepResult.attempts` (also stored in `wa_run_steps.attempts`) shows how many tries a step took. The final "Start export" click has no retry and must never get one.

## Gotchas

- **Sync Playwright API is used on purpose** (sequential steps, blocking user pauses). It cannot nest in one thread: a second `sync_playwright()` inside a running one raises. Tests that need two simultaneous managers run the second in another thread (see `test_locked_profile_gives_clear_error`).
- `ensure_safe_profile_dir` refuses any profile path inside the user's everyday Chrome `User Data`. Automation profiles live in `browser_data/<name>/` (gitignored, as are `logs/inspect/`, `exports/`, `.env`).
- Browser tests use a local HTTP server and throwaway `tmp_path` profiles (`tests/conftest.py`); they never touch the internet or `browser_data/`. Page-dependent JS like `navigator.userAgentData` needs a real loaded page, not `about:blank`.
- Security rules that apply to all code (see the README's Safety section): never log cookies/tokens/passwords, never bypass auth/CAPTCHA (pause for manual entry instead), never execute code from JSON, and never auto-retry the final export submission.
